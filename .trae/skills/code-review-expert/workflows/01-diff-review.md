# 01 · 变更级审查工作流（Git Diff）

> 适用：用户说「review 我的改动 / 这次 diff / 检查这个 commit / 上线前看看这次的变更」。
> 前置：**必须先执行** `workflows/00-preflight.md`（Step A 判定粒度=变更级，Step B 加载上下文，Step C 读取完整上下文）。

---

## 目标

只审查**本次变更引入**的问题，覆盖指定维度（默认全量五维度），并评估其对核心链路的**回归风险**。

---

## 执行步骤

### 1. 采集变更范围

```bash
git status -s                 # 文件级变更清单（新增/修改/删除）
git diff                      # 工作区未暂存变更
git diff --staged             # 暂存区变更
git log --oneline -n 20       # 判断基准与提交信息规范
git diff <base>...HEAD        # 指定区间（如 main...HEAD）
```

- **必须显式记录基准**（工作区 / 暂存区 / 某 commit），报告中注明。
- 若变更集为空 → 明确告知用户「无变更可审」，并建议改用模块级/项目级。

### 2. 变更归类（先分类，再逐项检查）

| 类别 | 审查看重点 |
| --- | --- |
| 新增代码 | 是否引入新逻辑缺陷、是否补充了对应测试 |
| 修改代码 | 是否破坏既有行为（回归）、调用点是否同步更新 |
| 删除代码 | 是否有残留引用/死代码、契约是否需同步 |
| 配置/契约变更 | 前后层是否一致（见 `SKILL.md`（§七 项目专属审查要点）） |

### 3. 逐文件执行五维度检查

对每个变更文件，按 `references/dimensions.md` 的检查点逐项过一遍（维度范围以 Step A 为准，默认全量）。

### 4. 回归风险评估（强制）

对涉及以下内容的变更，**必须**明确写出影响面：
- **统一契约**：`success` / `meta{timings,degraded,aiMode}` / `match.level` / `hits` / `gaps` 等字段的增删改。
- **请求链**：前端 → BFF → Java → Python → LLM 任一层接口签名、字段名（驼峰/蛇形）、错误码变化。
- **降级路径**：LLM 失败时的 HTTP 状态与 `meta.degraded`/`meta.aiMode` 行为是否被破坏。
- **共享状态**：`frontend/src/stores/` 中 Pinia store 的公共 API 变更（会影响所有消费者视图）。

### 5. 区分「本次引入」与「历史遗留」

- 通过 `git blame` 判断问题首次出现的提交。
- 报告中对历史遗留问题标注「**（历史遗留）**」，避免归咎于本次变更。

---

## 输出

严格按 `references/report-template.md` 输出。变更级报告**必须包含**：

1. **审查范围**：基准 + 变更文件清单（文件路径 + 行数增删）。
2. **按五维度**（或指定维度）分组的问题清单（🔴/🟡/🟢 + 文件行号链接 + 修改建议）。
3. **回归风险结论**：明确「是否影响核心链路 / 影响哪些既有功能」。
4. **上线建议**：可上线 / 需修复后上线 / 需补充验证。
