# references · 五大审查维度完整检查点清单

> 本清单是审查的**唯一检查点基线**。除非用户明确限定维度（见 `SKILL.md`（§2.2 第二步：判定审查维度 → 过滤检查点）），否则**每个维度下的检查点必须逐项覆盖，不得跳项**。
> 每条检查点统一标注：**判定标准** → **本项目关注点** → **典型问题示例**。

---

## 维度一 功能正确性与业务逻辑

### 1.1 需求匹配
- **判定标准**：实现是否完整满足需求描述；是否存在多做（越权扩范围）或少做（遗漏分支）。
- **本项目关注点**：四接口（analyze / match-job / optimize-resume / radar）的返回字段是否与 `contracts/openapi.yaml` 一致；评分公式是否与约定一致（`score = round(100 × (0.6×mandatory + 0.3×optional + 0.1×levelFit))`）。
- **典型问题**：字段名拼写与契约不符；`level` 取值不在 `EXCELLENT|GOOD_FIT|PARTIAL_FIT|WEAK_FIT` 枚举内；漏实现某分支（如未处理空简历）。

### 1.2 边界与异常处理
- **判定标准**：空值/极值/非法输入/超长输入是否被处理；异常是否被捕获且语义正确；是否吞异常。
- **本项目关注点**：
  - 空简历/空 JD 是否拦截（前端按钮禁用 + 后端校验双保险）。
  - LLM 失败是否走降级（HTTP 200 + 规则结果 + `meta.degraded=true`、`aiMode=rule`），**不得**抛 5xx 或丢字段。
  - 上游超时是否有明确异常（Java 侧 `UpstreamTimeoutException`）。
- **典型问题**：`resume_text` 为 `null` 未防御；`except` 捕获过宽且静默 `pass`；LLM 异常直接 `raise` 导致链路 500。

### 1.3 控制流清晰度
- **判定标准**：无深层嵌套、无不可达分支、无重复条件、无「先赋值后覆盖」的死逻辑。
- **本项目关注点**：降级分支与正常分支是否互斥且完备；`AI_MODE=llm|hybrid|rule` 三档位是否都有明确处理。
- **典型问题**：同一条件在 `if/elif` 中重复；`return` 后仍有副作用语句；异常处理分支永远走不到（死代码）。

## 维度二 性能与稳定性

### 2.1 资源消耗
- **判定标准**：无无界增长；无大对象/大字符串全量拷贝；无循环内重复计算；前端无内存泄漏（未清理的监听器/定时器/图表实例）。
- **本项目关注点**：长文本 LLM 调用是否有长度上限；前端 `echarts` 实例是否在 `onBeforeUnmount` 中 `dispose`；`window` 事件监听是否成对注册/移除。
- **典型问题**：`window.addEventListener('resize')` 未在卸载时移除；拼接大字符串逐字符 `+=`。

### 2.2 IO / 数据库操作
- **判定标准**：无 N+1 查询；批量化写入；连接/游标正确释放；避免同步阻塞主线程。
- **本项目关注点**：BFF 的 `better-sqlite3` 写库是否为同步且事务化；是否有未加索引的查询；HTTP 转发是否有超时设置。
- **典型问题**：循环内逐条 `insert`；每次请求新建 DB 连接；JSON body 未限制大小。

### 2.3 并发与锁
- **判定标准**：共享可变状态是否被并发安全访问；串行化是否正确；是否存在竞态。
- **本项目关注点**：Node 单线程下 `async` 共享变量；Python 端 `AI_MODE` 全局状态是否只读；SQLite WAL 下的并发写。
- **典型问题**：多请求共享并复写了同一全局可变对象；异步流程中读改写非原子。

### 2.4 依赖服务超时与降级
- **判定标准**：对下游调用必须有超时；下游失败必须有降级或友好错误；重试需有次数上限与退避。
- **本项目关注点**：Java `RestTemplate` 连接/读取超时；LLM 调用超时；BFF `callJava` 失败返回结构化错误而非挂起。
- **典型问题**：未设置超时导致请求悬挂；无上限重试放大故障；降级结果与正常结果结构不一致（前端解析失败）。

## 维度三 代码规范与可维护性

### 3.1 命名格式
- **判定标准**：命名与语言/项目约定一致、含义清晰、无拼音/无缩写歧义。
- **本项目关注点**：TS/Vue 用 camelCase（文件名视约定）；Python 用 snake_case；Java 用 camelCase + 类名 PascalCase；跨层字段名遵守「Java 驼峰 / 前端与 BFF 蛇形」约定。
- **典型问题**：TS 文件中混入 snake_case 局部变量；Java DTO 字段名与前端契约不一致。

### 3.2 复杂度与重复
- **判定标准**：函数单一职责、圈复杂度可控；无复制粘贴式重复；无魔法数字/硬编码。
- **本项目关注点**：相似逻辑是否抽为公共函数；分档阈值（85/70/50）是否集中定义；超时/端口等常量是否来自配置。
- **典型问题**：同一校验逻辑在 BFF/Java 各写一遍且不一致；阈值散布在多个文件。

### 3.3 注释与文档
- **判定标准**：注释解释「为什么」而非「做什么」；公共 API 有说明；无过时/误导注释；无残留调试代码。
- **本项目关注点**：store/工具函数是否有职责与数据流说明；是否残留 `print`/`console.log` 调试输出；`DELIVERY.md` 与实际行为是否一致。
- **典型问题**：删除逻辑但注释未更新；`# TODO` 长期堆积；生产代码残留 `console.error` 调试噪声（需评估是否为有意的错误上报）。

## 维度四 测试覆盖与可观测性

### 4.1 测试充分性
- **判定标准**：新增/变更逻辑有对应测试；覆盖正常路径 + 边界 + 异常/降级；测试可独立运行、无外部强依赖。
- **本项目关注点**：四端测试是否同步（前端 vitest / BFF vitest / Java JUnit+MockMvc / Python pytest）；降级路径是否有专门用例（LLM 失败 → `aiMode=rule`）；契约字段是否有断言。
- **典型问题**：只测 happy path，未覆盖降级/空值；测试依赖真实网络或真实 LLM；新增字段无断言。

### 4.2 监控与日志
- **判定标准**：关键路径有结构化日志；日志含足够定位信息且**不含敏感数据**；错误可追踪。
- **本项目关注点**：各层请求耗时是否透传（`meta.timings{bff,java,python,llm,total}`）；降级是否被明确标记；日志是否泄露 API Key。
- **典型问题**：捕获异常后不打日志（问题不可观测）；日志打印完整请求体导致敏感信息外泄；降级静默无痕。

## 维度五 提交规范与架构评估

### 5.1 提交粒度
- **判定标准**：提交原子、单一目的；提交信息遵循约定式提交（`feat/fix/docs/refactor/test/chore`）；无夹带无关变更；无提交依赖/构建产物。
- **本项目关注点**：可参考既有提交风格（如 `feat(contract): ...`、`fix(bff): ...`）；确认未误提交 `node_modules/`、`dist/`、`.env`、`bff/data/*.db`。
- **典型问题**：一次提交混合多个无关功能；提交信息为「update」「修改」等无意义描述；提交了密钥文件。

### 5.2 架构合理性
- **判定标准**：分层清晰、职责单一、依赖方向正确；无跨层直连；契约单一事实来源；无重复实现。
- **本项目关注点**：
  - 五层链路（前端 → BFF → Java → Python → LLM）职责边界是否被破坏（如前端直连 Java/Python）。
  - `contracts/` 是否为唯一契约源，是否存在契约与实现漂移。
  - 前端共享状态是否遵循「单一数据源 + 持久化 + 跨标签页同步」范式，是否存在多份本地状态。
  - 降级与统一响应结构是否在各层保持一致的语义。
- **典型问题**：绕过 BFF 直连下游；契约文件与实现字段不一致；同一状态在本地 `ref` 与全局 store 各存一份导致不一致。

## 使用方式

1. 依 Step A 确定维度范围：**未指定 → 全量五维度**。
2. 逐维度、逐检查点核对，命中问题的项按 `references/report-template.md` 记录（含文件行号链接与建议）。
3. 未命中但有风险的项标注「待确认」，**禁止臆断**。
